# Project Map 安装、部署与更新

本文说明如何将 Project Map 部署到 Codex Desktop 和目标项目，以及如何在多台电脑之间快速同步、验证、更新和回滚。

> 适用范围：本能力包面向 Codex 本地工作区，不是普通 ChatGPT 对话中的云端插件。ChatGPT/Codex Desktop 的账号或任务同步不应被当作本机 Skill、CLI 或项目文件的部署机制。

## 文档职责与单一事实来源

为避免安装说明在多个文件之间漂移，维护时遵守以下边界：

| 文件 | 唯一职责 |
| --- | --- |
| `install.sh` | macOS/Linux 一键安装的实际行为、默认值与参数 |
| 本文 | 手工安装、Windows、部署模型、更新、回滚、验收与排障 |
| `README.md` | 项目概览、唯一的一键安装入口与日常使用示例 |
| `docs/design/`、`docs/superpowers/plans/` | 历史设计和实施证据，不作为运行手册 |

规则：精确的手工安装命令只在本文维护；README 不复制这些命令。脚本默认值变更时，必须同步本文并由测试校验。历史文档中的命令即使保留，也不得作为当前安装依据。

## 部署模型

Project Map 分发与完整工作流包含五个需要分别安装或同步的层次，其中源码层是发布来源，其余四层是运行时验收对象：

| 层次 | 内容 | 建议同步方式 |
| --- | --- | --- |
| GSD 层 | GSD runtime 与 `gsd-*` Skills | 每台设备单独安装固定 GSD 版本 |
| 源码层 | CLI、Skill、Capability 和文档 | Git 远程仓库 + 版本标签 |
| Codex Skill 层 | `capability/skills/project-map/` | 每台设备安装到 `~/.agents/skills/project-map` |
| 项目 CLI 层 | `project-map` 命令 | 目标项目安装固定 Git 标签或私有 npm 版本 |
| 项目数据层 | `.planning/project-map/` | 随目标项目 Git 仓库同步；新项目显式初始化 |

推荐的多端模型：

```text
Project Map Git 远程仓库
       ├─ 设备 A：克隆指定标签 → 链接 Skill
       ├─ 设备 B：克隆指定标签 → 链接 Skill
       └─ 设备 C：克隆指定标签 → 链接 Skill

目标项目 Git 仓库
       └─ 同步 `.planning/project-map/` 与固定的 CLI 依赖
```

## 每台设备的五分钟部署清单

远程仓库已经可用；若尚无发布标签，可以先使用 `main` 验证，但这不属于稳定、可复现发布：

1. 安装 Git、Codex CLI 或 Codex Desktop；完整安装 GSD 1.11.0 使用 Node.js 24+，仅使用 Project Map 时使用 Node.js 18+。
2. 如需 GSD 交接，安装固定版本 GSD，并确认所需的 `gsd-*` Skills 可见。
3. 将 `project-map` 安装到用户级发现目录 `~/.agents/skills/project-map`。
4. 克隆目标项目并运行 `npm ci`，确认 `node_modules/.bin/project-map` 存在。
5. 已有 Project Map 时运行 `npx project-map check --json`；新项目则显式运行 `init`。
6. 重启 Codex 或新建任务，用 `/skills` 或输入 `$project-map` 验证发现结果。
7. 若项目要求 `$gsd-debug`，单独确认 `~/.agents/skills/gsd-debug/SKILL.md` 存在。

这七步不包含任何手工复制项目数据的操作。Git 负责源码和项目状态的跨端传输，本机 Skill 安装只负责让 Codex 发现工作流说明。

## 每条安装命令实际提供什么

| 命令或动作 | 会安装／生成 | 不会安装／生成 |
| --- | --- | --- |
| `$skill-installer ... capability/skills/project-map` | 一个 `project-map` Skill | GSD、项目 CLI、`.planning/project-map` |
| `npx @opengsd/gsd-core...` | GSD runtime、Agents 与 `gsd-*` Skills | `project-map` Skill、项目 CLI 与数据 |
| 目标项目执行 `npm install` / `npm ci` | 项目本地 `project-map` CLI | Codex Skill、GSD、项目数据 |
| `npx project-map init ...` | `.planning/project-map` 初始数据 | Codex Skill、GSD、CLI 依赖 |

只有四项都通过各自验收，才能宣称完整的 GSD + Project Map 工作流已部署。

## 推荐：克隆后运行一键安装

macOS 或 Linux 上，用户只需克隆本仓库并指定目标项目：

```bash
git clone https://github.com/githuangjunwen/Project-initialization-skill.git
cd Project-initialization-skill
./install.sh --project /opt/my-project
```

`/opt/my-project` 只是示例，必须替换为目标项目中真实存在且包含 `package.json` 的目录。若源码仓库就位于目标项目内，例如 `/opt/my-project/Project-initialization-skill`，进入源码仓库后可直接运行 `./install.sh --project ..`。不要原样复制 `/absolute/path/to/target-project` 一类占位符。

该命令会：

1. 检查 Git、Node.js、npm 与 npx；安装 GSD 1.11.0 时要求 Node.js 24+。
2. 默认安装 GSD `1.11.0` core profile，只暴露 8 个核心 GSD Skills；并确认 `gsd-new-project` 与 `gsd-surface` 可见。
3. 将当前克隆中的 `project-map` Skill 安装到 `$HOME/.agents/skills/project-map`。
4. 将目标项目的 CLI 依赖锁定到当前克隆的 Git commit，而不是漂移的 `main`。
5. 已有 `.planning/project-map` 时运行 `check`；没有时明确提示尚未初始化。

首次初始化也可以在同一条命令完成，但必须由用户提供真实输入：

```bash
./install.sh \
  --project /opt/my-project \
  --init-title "项目名称" \
  --init-text "项目的原始想法"
```

常用选项：

- `--skip-gsd`：设备已由其他方式管理 GSD 时跳过 GSD 安装。
- `--skip-cli`：只部署设备级 GSD 与 Skill，不修改任何目标项目。
- `--force-skill`：现有 Skill 内容不同时，先备份再替换。
- `--gsd-version` / `--gsd-profile`：显式覆盖默认 GSD 基线；profile 可选 `core`、`standard` 或 `full`，默认 `core`。
- `--gsd-profile full`：项目确实需要 `$gsd-debug`、审计、安全、UI、AI Eval 等扩展能力时启用完整表面。
- `--allow-dirty`：允许从有未提交改动的开发克隆安装；正式部署不应使用。

脚本支持重复执行：内容一致的 Skill 会跳过；不同内容默认停止，避免覆盖来源不明的安装。当前只支持 macOS 与 Linux，Windows 继续使用后文 PowerShell 步骤。

## 边界与原则

### Skill 不等于 CLI

Skill 负责识别“推进 E-002”等意图并约束工作流。`project-map` CLI 负责读写 `.planning/project-map/` 中的数据。只安装其中一个都不完整。

### Desktop 同步不等于文件部署

`~/.agents/skills/`、GSD runtime、Node.js 依赖和项目工作区都是设备上的文件。多台设备即使登录同一账号，也必须在每台设备完成相应安装。

### 开发态与稳定版分开

- 开发态：使用文件链接，源码保存后立即生效。
- 稳定版：使用 Git 标签或私有 npm 版本，确保多台设备行为一致。

## 安装前提

每台设备需要：

- Git。
- Project Map CLI 需要 Node.js 18 或更高版本。
- 默认安装的 GSD 1.11.0 需要 Node.js 24 或更高版本；Node.js 18–23 只能配合 `--skip-gsd` 使用本项目自身能力。
- Codex CLI 或能打开本地代码工作区的 Codex Desktop。
- Project Map 源码仓库和目标项目仓库的访问权限。
- 如需 GSD 交接，还需要单独安装兼容的 GSD runtime；本项目当前核对基线为 `1.11.0`。

克隆源码后先运行：

```bash
node --version
npm --version
npm run check
```

## 方案 A：本机开发态热同步

### macOS/Linux 安装 Skill

远程仓库安装的推荐方式是不必先克隆本仓库，直接调用 Codex 自带安装器并显式指定官方用户级发现目录：

```bash
python3 "${CODEX_HOME:-$HOME/.codex}/skills/.system/skill-installer/scripts/install-skill-from-github.py" \
  --repo githuangjunwen/Project-initialization-skill \
  --path capability/skills/project-map \
  --ref main \
  --dest "$HOME/.agents/skills"
```

不要省略 `--dest`。当前内置安装器默认写入 `${CODEX_HOME:-$HOME/.codex}/skills`，而 Codex 的用户级本地 Skill 发现目录是 `$HOME/.agents/skills`。

如尚无发布标签，开发验证可以使用 `--ref main`。稳定部署时把 `main` 替换为已发布标签或完整 commit SHA；安装器在目标目录已存在时会停止，不会静默覆盖旧版本。是否已有标签应通过本文“发布状态检查”的命令实时确认。

如果已经克隆本仓库并希望开发态热同步，再建立链接。安装前先确认没有同名目标：

```bash
test ! -e ~/.agents/skills/project-map
```

然后建立链接：

```bash
mkdir -p ~/.agents/skills

ln -s \
  /absolute/path/to/Project-initialization-skill/capability/skills/project-map \
  ~/.agents/skills/project-map
```

如果已存在同名目录或链接，不要直接覆盖。先用下列命令确认来源：

```bash
readlink ~/.agents/skills/project-map
```

### Windows PowerShell 安装 Skill

```powershell
New-Item -ItemType Directory -Force "$env:USERPROFILE\.agents\skills"
New-Item -ItemType Junction `
  -Path "$env:USERPROFILE\.agents\skills\project-map" `
  -Target "C:\absolute\path\to\Project-initialization-skill\capability\skills\project-map"
```

完成后新建 Codex 任务。如果仍未识别 Skill，再完全退出并重新打开 Codex Desktop。

### 在目标项目安装 CLI

单机开发可使用本地路径：

```bash
cd /absolute/path/to/target-project
npm install --save-dev /absolute/path/to/Project-initialization-skill
```

验证：

```bash
test -x node_modules/.bin/project-map && echo "project-map 已安装"
```

> 绝对路径仅适合单机开发。不要将包含 `/Users/...` 或 `C:\Users\...` 的依赖记录当作多端标准。

## 方案 B：个人多设备快速部署

这是 ChatGPT/Codex Desktop 多端使用的推荐方案。

如果只想使用发布仓库中的 Skill，无需克隆本仓库，直接执行“macOS/Linux 安装 Skill”中的安装器命令即可。只有开发态热同步或安装项目 CLI 的本地路径版本时才需要克隆源码。

### 1. 建立唯一发布源

1. 将本仓库推送到每台设备都能访问的 Git 远程仓库。
2. 每次发布同时更新 `package.json` 和 `capability/capability.json` 版本。
3. 运行 `npm run check`。
4. 创建并推送不可变标签，例如 `<release-tag>`。

```bash
git tag -a <release-tag> -m "release: <release-tag>"
git push origin main
git push origin <release-tag>
```

多台设备不应直接跟随未固定的 `main` 分支，否则 Skill 行为和 CLI 数据规则可能不一致。

### 2. 每台设备克隆同一版本

```bash
git clone <仓库远程地址> Project-initialization-skill
cd Project-initialization-skill
git checkout <release-tag>
npm run check
```

然后按“方案 A”链接 Skill。由于克隆被锁定到标签，既便于更新，又不会意外跟随开发分支。

### 3. 目标项目使用可移植依赖

推荐使用带标签的 Git 依赖：

```bash
cd /absolute/path/to/target-project
npm install --save-dev \
  "git+https://github.com/githuangjunwen/Project-initialization-skill.git#<tag-or-full-commit>"
```

如果使用私有 npm 注册表：

```bash
npm install --save-dev project-map-capability@<version>
```

提交目标项目的 `package.json` 和锁定文件。其他设备克隆目标项目后只需执行：

```bash
npm ci
```

## 方案 C：团队或多项目稳定部署

1. 通过代码审查合并源码更新。
2. 两个清单文件使用相同版本。
3. CI 运行 `npm run check`。
4. 创建签名或受保护的版本标签。
5. CLI 发布到私有 npm，或使用固定 Git 标签。
6. 目标项目通过依赖更新 PR 升级，不自动跟随最新分支。
7. 每台 Codex Desktop 设备将 Skill 链接到本机的固定版本克隆。

如果不希望在全局 `~/.agents/skills/` 暴露 Skill，应优先使用仓库级 `.agents/skills/project-map` 或 GSD 项目级 Capability，并固定已验证的 GSD 版本。

## GSD runtime 与 Skills 安装

`project-map` 不会附带 GSD。需要完整交接工作流时，每台设备单独执行：

```bash
npx -y @opengsd/gsd-core@1.11.0 --codex --global --profile=core
```

验证 runtime 与 core profile 必备 Skill：

```bash
test "$(cat "$HOME/.codex/gsd-core/VERSION")" = "1.11.0"
test -f "$HOME/.agents/skills/gsd-new-project/SKILL.md"
test -f "$HOME/.agents/skills/gsd-surface/SKILL.md"
```

GSD 1.11.0 的 `core` profile 暴露 8 个常用 Skill：`new-project`、`discuss-phase`、`plan-phase`、`execute-phase`、`phase`、`help`、`update` 和 `surface`。`standard` 暴露 15 个，`full` 才暴露全部约 70 个。

如果项目明确要求 `gsd-debug` 或其他扩展 Skill，可以重新执行 `./install.sh --project <真实项目路径> --gsd-profile full`，也可以在 Codex 中运行 `$gsd-surface profile full` 后完全重启 Codex。需要恢复精简表面时运行 `$gsd-surface profile core`。不要手工删除 `gsd-*` Skill 目录。

## GSD Capability 安装

当本机存在 GSD 1.11.0 runtime 时，在目标项目根目录通过实际的 `gsd-tools.cjs` 入口执行：

```bash
GSD_TOOLS="${CODEX_HOME:-$HOME/.codex}/gsd-core/bin/gsd-tools.cjs"

node "$GSD_TOOLS" capability install \
  /absolute/path/to/Project-initialization-skill/capability \
  --scope project \
  --yes

node "$GSD_TOOLS" capability list --scope project --raw
```

该方式属于高级项目级集成，不是 GSD runtime 安装命令，也不是多端分发中心。如果 GSD 安装器复制了 Skill，升级源码后必须重新安装并验证列表。

## 目标项目的首次初始化

```bash
npx project-map init \
  --project-title "项目名称" \
  --text "项目的原始想法"
```

`init` 会拒绝覆盖已有 Project Map。建议将以下内容提交到目标项目的 Git 仓库：

- `.planning/project-map/index.json`
- `.planning/project-map/sources/`
- `.planning/project-map/nodes/`
- `.planning/project-map/decisions/`
- `.planning/project-map/CURRENT.md`
- `.planning/project-map/PROJECT-MAP.md`
- `package.json` 和锁定文件

如果需求文档包含敏感商业信息，应使用私有仓库并确认数据分类要求。不要用聊天记录代替项目仓库保存规范数据。

## 多设备日常操作协议

Project Map 的规范 JSON 应当使用“同一时间只由一台设备写入同一分支”的规则。任务开始前：

```bash
git status --short
git pull --ff-only
npm ci
npx project-map check --json
```

任务结束前：

```bash
npx project-map check --json
git status --short
git add .planning/project-map package.json package-lock.json
git commit -m "docs: 更新项目地图"
git push
```

如果两台设备已同时修改项目地图：

1. 停止继续写入。
2. 不要手工合并 `CURRENT.md`、`PROJECT-MAP.md` 或就绪标记。
3. 根据权威来源合并 `sources/`、`nodes/`、`decisions/` 和 `index.json`。
4. 运行 `npx project-map check --json`。
5. 检查通过后才能运行 `npx project-map rebuild --json`。

## 更新流程

### 发布新版本

1. 完成源码和文档更新。
2. 同时更新 `package.json` 与 `capability/capability.json` 版本。
3. 更新兼容性或迁移说明。
4. 运行 `npm run check`。
5. 提交变更，创建并推送版本标签。

发布前检查：

```bash
node -p "require('./package.json').version"
node -p "require('./capability/capability.json').version"
npm run check
git status --short
```

两个版本号必须一致，发布前工作区应当干净。

### 升级每台设备

```bash
git fetch --tags
git checkout <release-tag>
npm run check
```

- Skill 是文件链接时，检出新标签后就已更新。
- Skill 是复制或 GSD Capability 安装时，需重新安装。
- 目标项目需升级 CLI 依赖并提交新锁定文件。

升级后在目标项目验证：

```bash
npm ci
npx project-map check --json
```

然后新建 Codex 任务，输入“查看项目状态”或“推进 <ID>”验证 Skill 路由。

## 回滚流程

回滚时必须同时对齐 Skill 和 CLI：

1. 每台设备检出上一个稳定标签。
2. 将目标项目的 CLI 依赖回退到同一版本。
3. 重新执行 `npm ci`。
4. 运行 `npx project-map check --json`。
5. 新建 Codex 任务验证 Skill。

`project-map check` 通过之前不要运行 `rebuild`。如果新版本改变了规范数据结构，必须使用该版本提供的迁移流程，不得根据生成的 Markdown 手工重建数据。

## 部署验证清单

- [ ] 源码克隆检出的标签与预期版本一致。
- [ ] `npm run check` 通过。
- [ ] `~/.agents/skills/project-map/SKILL.md` 存在，并来自预期版本。
- [ ] 新建 Codex 任务能发现 `project-map` Skill。
- [ ] 如需 GSD，`~/.codex/gsd-core/VERSION` 与要求一致，所需的 `~/.agents/skills/gsd-*/SKILL.md` 均存在。
- [ ] 目标项目的 `node_modules/.bin/project-map` 存在。
- [ ] CLI 版本与 Skill 源码版本一致。
- [ ] `npx project-map check --json` 通过。
- [ ] `.planning/project-map/` 已纳入合适的目标项目 Git 仓库。
- [ ] 多台设备的目标项目处于同一依赖锁定版本。
- [ ] 敏感需求信息没有进入不合适的公开仓库。

## 常见问题

### Codex 没有识别 Skill

1. 确认 `~/.agents/skills/project-map/SKILL.md` 存在。
2. 如使用链接，确认链接目标在本机存在。
3. 确认没有只安装到 `~/.codex/skills/project-map`；该目录不是当前用户级发现目录。
4. 在 Codex CLI 中运行 `/skills` 或输入 `$project-map` 验证显式发现。
5. 新建 Codex 任务；仍无法识别时，完全退出并重启 Codex。

### 能看到 project-map，但看不到 GSD Skills

`project-map` 与 GSD 是独立安装。先检查：

```bash
test -f "$HOME/.codex/gsd-core/VERSION"
find "$HOME/.agents/skills" -mindepth 2 -maxdepth 2 -path '*/gsd-*/SKILL.md' -print
```

runtime 不存在时执行本指南的 GSD 安装命令；只缺少个别 GSD Skill 时检查 GSD surface/profile。

### Skill 被识别，但 CLI 不可用

在当前目标项目重新执行 `npm install` 或 `npm ci`，并确认 `node_modules/.bin/project-map` 存在。

### 两台设备行为不同

依次比较 Git 标签、目标项目锁定文件、Skill 链接指向、Node.js 版本、GSD 版本和 Capability 安装方式。

### 升级后生成文档仍是旧内容

```bash
npx project-map check --json
npx project-map rebuild --json
```

只有第一条命令通过后才能运行第二条。

## 发布状态检查
